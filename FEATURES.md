# Features — what the core implements

A map of every feature of the coordinator core, for the **machines that test it** — one session per
feature, looking for holes — and for people who want to see what is there.

**How to use it (a tester):** take one ID; read its block and every file it names; try to break each
`promises` line on a real or throwaway project; anything that breaks is a core finding, reported through
[procedures/CORE-FINDINGS.md](procedures/CORE-FINDINGS.md) (an issue titled `[core-report] …`). A block
says what is already tested (`tested by`) and what is known to be open (`not covered`), so a tester
starts where the core is weakest. The rules themselves live in the files a block names; this map only
points to them and never replaces them.

**Testing it:** [tests/FEATURE-TEST.md](tests/FEATURE-TEST.md) is the prompt for a tester session — one group or
feature per session, a fixed report.

**Kept in sync:** `scripts/check-core` fails when a file a block names does not exist, when a script,
procedure, role or one-time step is in no feature, when an ID repeats, when a block lacks one of its
five fields, or when the table and the blocks disagree.

Block shape: `defined` (where the rule lives) · `entry` (what triggers it) · `promises` (checkable
statements) · `tested by` (tests, CI steps, self-test steps) · `not covered` (known gaps). A rule with
no test rests on the sessions following it: the likeliest place for a hole.

## START

### F-START-01 The one start sequence
- defined: CORE.md §2, procedures/INIT.md, README.md
- entry: any fresh session in a project; the link to this repository; this repository's own CLAUDE file
- promises: the nine steps run in order (identity → one coordinator → files → context, then the session-start housekeeping in a set-up project → open questions → quiz → platform and safety → the dry run's two real checks and the self-test → wait); after step 9 nothing starts until the owner gives a task or a batch command; a question is answered, never treated as an order (§1.2)
- tested by: none (model behaviour)
- not covered: no automated check that a session follows the order

### F-START-02 One coordinator per project
- defined: CORE.md §2
- entry: `claude agents --json` at start
- promises: another session whose name contains `Coordinator` and whose working directory is this project makes the coordinator ask the owner which one coordinates; sessions of other projects are told apart by their folder
- tested by: none
- not covered: two coordinators started at the same moment

### F-START-03 The coordinator's name
- defined: CORE.md §2, TOOLKIT.md, procedures/INIT.md
- entry: INIT 3.1 question 10; one-time step `coordinator-name`
- promises: the name contains the English word `Coordinator`; a session named otherwise asks the owner for `/rename`; the coordinator never renames itself; a rename is announced to every running session
- tested by: none
- not covered: whether every role's fallback finds a renamed coordinator

### F-START-04 The init quiz
- defined: CORE.md §3, procedures/INIT.md
- entry: step 6 of the start sequence; a new or adopted project
- promises: no worker and no change before every applicable question is answered and the summary gets a yes (§1.12); the fixed questions come first, in the same order every init, one setting each (strictness and spend level apart), their text and options as INIT 3.1 writes them, translated, the recommended option marked; clarifying questions only after them; what the project already shows is confirmed in one table, not asked
- tested by: none
- not covered: the quiz's wording is not checked against the fourteen questions

### F-START-05 Strictness presets
- defined: CORE.md §3, PROJECT.template.md
- entry: INIT question 1; one-time step `strictness`
- promises: the preset sets which tasks run, parallel workers, who merges, review, new tasks, production writes and the autopilot; a worker works alone inside its task in every preset; an older project is mapped to a preset only on the owner's yes
- tested by: none
- not covered: no automated check — it rests on the sessions following the rule

### F-START-06 Spend level
- defined: CORE.md §7, PROJECT.template.md
- entry: one-time step `spend-level`
- promises: the level tilts the choice between neighbouring rungs or efforts and sets when the top rung runs — lean: only an escalation after a failed review; balanced: also the `hardest` kinds and research runs (the researcher role, a lead's research; the radar stays light); thorough and the strict preset: also the verifier of risk-tier work and a `hard` task that failed its review once on Opus, risk-tier execution on the top rung only when `hardest`; the top rung only within the guard rails — the plan includes it (the owner's `fable-on-plan` answers), no limit or credits message since the weekly reset, the block with its top-rung runs at 2.5× fits the weekly cap (`run-stats --limits --block-top`), the top rung's weekly cost share (the `top` column) under 50%; effort is raised before the model; quality checks and the risk floors never depend on the level
- tested by: tests/run-stats/run.sh for the numbers the guard rails read (the `top` column, `--block-top`); the routing itself none
- not covered: choosing the rung rests on the coordinator following the rule

### F-START-07 Settings
- defined: CORE.md §13a, procedures/SETTINGS.md, PROJECT.template.md
- entry: the owner says "settings" in any wording
- promises: showing the settings changes nothing; a change is asked as a quiz with the current value and the recommendation first; `PROJECT.md` changes only on the answers
- tested by: none
- not covered: no automated check — it rests on the sessions following the rule

### F-START-08 "What is your task?"
- defined: CORE.md §13, procedures/WHAT-IS-YOUR-TASK.md
- entry: "Coordinator, what is your task?" in any wording
- promises: the answer covers the role, the work mode and what runs on events, the gates, who decides, and the rules in effect for this project
- tested by: none
- not covered: no automated check — it rests on the sessions following the rule

### F-START-09 Restart on the same machine
- defined: CORE.md §2, procedures/INIT.md
- entry: a journal exists and no live session carries the coordinator name
- promises: the coordinator asks for its name first, re-reads the local core, and subscribes to the running sessions instead of starting new ones
- tested by: none
- not covered: a restart while a worker waits on a permission prompt

### F-START-10 Sources of truth
- defined: procedures/SOURCES.md, CORE.md §4c
- entry: INIT question 4; anything the owner hands over (links, documents, screenshots)
- promises: one main system per kind of information; everything else goes to the catalog with a weight; evidence that contradicts a main source becomes a question to the owner; no tracker, host or git → the modes of SOURCES §3

- not covered: no automated check — it rests on the sessions following the rule

### F-START-11 Project scenarios
- defined: procedures/INIT.md

- promises: an empty folder gets infrastructure proposals with one yes each; an existing project is read before anything is asked; rules in other agents' formats are read, not overwritten
- tested by: none
- not covered: no automated check — it rests on the sessions following the rule

### F-WORK-06 Tests first
- defined: roles/tester.md, CORE.md §4, CONTRACT.md, scripts/check-contract.sh, scripts/check-contract.ps1, scripts/start-worker.sh, scripts/start-worker.ps1, roles/worker.md, roles/verifier.md, roles/lead.md
- entry: an oracle criterion with no test yet; every risky change (§5); a tester session (`#<task> tester: …`) by start-worker where the coordinator's own settings hold no guard or the run is long
- promises: the tester writes only test files; every contract records the decision in `tests_first` — `yes`, or `no` with its reason — and check-contract refuses one without it or with neither; its tests fail now for the reason the criterion names; the worker makes them green unchanged; what cannot be automated becomes an owner check; under a lead the tester commits nothing and returns its test files, which the sub-worker commits on the sub-branch that needs them, never on the integration branch; a tester reads another commit without moving a working copy (no checkout, switch, reset, stash or restore); a tester runs as a subagent only for a short run under a coordinator whose own settings hold the guard — else as a session under the worker safety file, so its push is guarded and its cost exact; a test checks what is visible from outside and an access point it needs is named in the contract or the test file's header, implemented as written; a wrong test goes back to the tester, the worker makes only build-only edits that change no check and names them; a flaky check is reproduced in three parts (load, a variant failing every time, a negative control) (#237); start-worker refuses a worker whose contract has `tests_first: yes` without `--tester-commit` or `--tester-tests` (F-WORKERS-01); on a §5 or `tests_first: yes` task every later round that changes behaviour starts with the tester, the coordinator's message names its new commit, and the verifier reports per round whether the new tests came from the tester or the worker (#276)
- tested by: tests/check-contract/run.sh (`tests_first` missing, `maybe`, a bare `no`; `yes` and a quoted `no - <why>` pass); tests/workers/run.sh (the start gate)
- not covered: whether a `no` is right, and whether the tester then ran, rest on the coordinator and the verifier; later rounds go by message, so only the rules and the verifier keep them (#276)

### F-WORK-07 Leads for large tasks
- defined: roles/lead.md, CORE.md §4, TOOLKIT.md
- entry: a task that would not fit one worker, or whose pieces must land together
- promises: the lead splits into sub-contracts, starts and verifies its workers, integrates on its own branch only and returns one PR and one report with every run's spend; a lead over its budget starts nothing new; its own share (often 30–100% of its workers' sum) is planned for and read at each stage by `$CLAUDE_CODE_SESSION_ID` (a reading that never holds the whole turn in progress: zero or partial on the first turn); while any worker runs it keeps one background wait alive so it stays reachable, and one gone `done` is resumed by the coordinator with the report that fell back to it; its sub-contracts, briefs and run notes live in its notes folder beside its worktree, `<its worktree>.lead/` (never inside the worktree, where the project's own checks read them; #310), never in the job's tmp; its verifier reviews the sub-branch's change and the lead runs the build and test oracles on its integration branch right after each merge, a failure going back to the worker; once the verdict on its PR is given the lead is closed (its session stopped, its spend read and the session removed; its working copy kept until the after-merge cleanup and reused), a small later round on that PR goes to a fresh worker on the integration branch with a short contract from the finding (the tester first where CORE §4 step 5 requires it), reviewed by the coordinator's verifier, as do, for that PR, the merge queue's CONFLICT, its HEAD MOVED / NOT APPROVED (or the verifier, for a new commit), a FAILED classified as code and a merge of main, and a lead is resumed only to re-split a round into several sub-contracts (#292); its final report is sent with SendMessage to the report address the brief names, the worker's fallbacks included, a report only in its own output never reaching the coordinator (#351)
- tested by: SELFTEST step 4 (a lead with two workers); tests/workers/run.sh (the `.lead/` exclude line, F-WORKERS-05; the notes folder beside the worktree, F-WORKERS-01 and F-WORKERS-06)
- not covered: the background wait, the self-read and the oracles after each merge rest on the lead following the rule; closing the lead after its verdict and sending later rounds to fresh workers rest on the coordinator (#292); whether an idle background session exits depends on the Claude Code version (seen on 2.1.296)

### F-WORK-08 The worker role
- defined: roles/worker.md, CONTRACT.md
- entry: a worker's brief
- promises: the worker changes only what the criteria need, works on its own branch, opens no PR its contract does not name (a lead's sub-contract merges into the integration branch, #331), proves each oracle itself, reports to the address in its brief with every criterion's evidence class and any suspected core fault in `core_findings`; stuck → a `blocked` report; waiting on CI it keeps a background wait (`gh pr checks --watch`) running until it reports; it never weakens, removes or rewrites the tester's tests and edits them only to make a test build or run, named in `test_edits`, any other change going back to the tester; on other tests the not-weakening edits are named too (a cycle wait to a time or state wait of the same value, a tolerance widened only on its own new check with a measured reason, a non-random starting state with every check unchanged and a negative control still failing); its report states `ci_seconds`, and a change over the project's CI time budget (default 30 s) is a question first; a check the verifier cannot repeat carries its raw output, a summary being a claim; a long local run is never under a short tool timeout (#237); a SendMessage a hook refused (an error or a timeout) is sent again once, refused again it goes to the fallback address and the report says so, never dropped silently (#290); a commit it has reported is never amended, rebased, reset or force-pushed in the same task, further changes are new commits and the next report names the new head, history rewritten only when the coordinator asks in so many words (#350)
- tested by: SELFTEST step 4
- not covered: none known
